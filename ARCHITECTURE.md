## Federation Architecture

```
Mastodon / Misskey / Pleroma
          │
          ▼
  TestagramGateway         ← HTTP Signature verification happens here
  (Node.js / Deno / Go)   ← WebFinger / Actor / Inbox / Outbox
          │
          ├── /timeline/*  ← React frontend polls via federation.ts
          ├── /follow       
          ├── /posts        
          └── /.well-known/webfinger
          │
          ▼
  Supabase PostgreSQL
  (activitypub_actors, activitypub_keys, activitypub_inbox,
   activitypub_outbox, federated_followers, federated_following,
   remote_accounts, remote_posts)
```

**Key principles:**
- The React frontend **never** verifies HTTP Signatures — this lives in TestagramGateway
- RSA key pairs are generated by the `activitypub-keygen` Edge Function using Web Crypto API
- Edge functions `activitypub-actor`, `activitypub-inbox`, `activitypub-webfinger` are lightweight stubs that redirect to the Gateway

## Data Flow — User Signs Up

1. Supabase Auth creates `auth.users` row
2. `handle_new_user` trigger creates `user_profiles` row
3. `on_user_profile_activitypub` trigger creates `activitypub_actors` row
4. `AuthProvider.tsx` calls `activitypub-keygen` Edge Function
5. Edge Function generates RSA-2048 key pair, stores in `activitypub_keys`
6. User can now be discovered via WebFinger through TestagramGateway

---

## Data Flow — Receiving a Follow from Mastodon

1. Mastodon sends `POST /inbox` to TestagramGateway
2. Gateway verifies HTTP Signature using actor's `publicKeyPem`
3. Gateway stores activity in `activitypub_inbox`
4. Gateway upserts follower in `federated_followers`
5. Gateway sends `Accept` activity back to Mastodon inbox
6. React frontend shows updated follower count from `federated_followers`
